Project notes

DLeo Bug Detective

A developing website-diagnostics project focused on selected checks and findings that a person can review. This page separates the project's current description from future goals; it is not a claim that every planned feature is already implemented.

← Back to project directory
Scope

What the project currently does

The implemented DLeo command-line tool runs locally. It can check its own basic readiness and perform a limited HTTP/HTTPS review of a website you own or are authorized to assess. The portfolio itself is not a hosted scanner.

Local health check

The doctor command checks the local tool's readiness. It is separate from scanning a website and does not prove that every subsystem is healthy.

Authorized website scan

A scan reports the HTTP status, response time, final origin, and selected HTTP security-header findings. These are limited signals, not a complete security assessment.

Optional local report

JSON export is opt-in. Reports are saved locally and are sanitized to omit URL paths, query strings, fragments, response bodies, and raw header values.

Human-readable findings

Treat results as leads for review, not a final verdict. Confirm important findings against the site and relevant documentation before changing anything.

Suggested workflow

Use it carefully

  1. Choose a website you own or have explicit permission to assess.
  2. Run only checks that are available in the actual tool; this documentation does not imply every possible check exists.
  3. Read each result and its explanation, then independently verify important findings.
  4. Make changes only when you understand their effect, and retest using an appropriate method.
Boundaries

What it does not promise

  • It is not a complete security audit or penetration test.
  • It does not prove that a website is safe or unsafe.
  • It is not antivirus, a firewall, a VPN, or automatic device protection.
  • A missing warning does not mean that no issue exists; a warning may also need context.
Development priorities

What should improve next

Accuracy and edge cases

Test how checks behave across different site configurations and make uncertain outcomes clear.

Planned improvement

Better explanations

Explain what each check examined, why the result matters, and what a user should verify.

Planned improvement

Transparent reporting

Make the limits of each check visible so users do not mistake a small set of checks for full coverage.

Planned improvement

Evidence before claims

Document a feature as available only after it has been implemented and tested.

Project principle
Responsible use

Permission first

Only assess websites you own or have permission to test. Do not use the project to disrupt services, bypass access controls, or probe systems without authorization. When in doubt, ask the site owner first.
